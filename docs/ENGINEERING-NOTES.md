# Engineering notes

The reasoning, measurements, run ids and incidents behind the rules in `AGENTS.md`.
`AGENTS.md` states each rule in short and is loaded into every agent session; this file keeps the full record and is read on demand.
Read the matching entry here before changing anything a rule there names.

Each section below is the text `AGENTS.md` carried under the same heading before it was trimmed, so every fact, run id and measurement survives.

## Working here

- `npm run check` is the whole gate; `README.md` explains what each step is and why.
- Dependency direction for `src/` is the layer list in `scripts/check-deps.js`; add a new module to a layer there or the check fails.
- The product name is a parameter: `package.json` `name`, derived through `src/identity.js`; never write it as a literal under `src/`.
- A review has a bounded lifecycle.
  The daemon idles out on inactivity (`touch` in `src/server.js`), and a tab keeps it alive only by heartbeating while visible (`startHeartbeat` in `src/browser/chrome.js`, paced by the `idleMs` that `/health` reports), so an abandoned tab releases the process instead of pinning it open.
  `SessionStore.#evict` disposes the least-recently-active session (an ended review first, never one with a poll attached or within its grace, a tab open, or notes not yet sent or received) when `open` hits `limits.sessions`, so `sessions/` in the state directory stays bounded.
  `test/server.test.js` and `test/browser.test.js` prove the idle-out, and `test/session-store.test.js` the bound.
  The tab rule (`live` from `EventStreams.live`) fixes 0.1.6, where the tab heard nothing and answered every note with "no such session", the agent's reopen said the tab was open and opened none while the tab's page answered 404, and closing the newer of two tabs read the gone session in a socket `close` handler and took the daemon down.
  When every held session is in use in one of these ways the new open is refused with a 429 that says so, rather than breaking a review someone is in; a tab that was disconnected when its session went is refused with a 4404 on its return (it does not reconnect), says to ask the agent to open the file again, and that opens a fresh tab.
  `test/cli.test.js` proves the spared review and the refusal against a real daemon, and `test/browser.test.js` the returning tab's notice and the fresh tab.
- Each session is its own file under `sessions/` (`#persist` in `src/session-store.js`), so a write costs one session whatever the count; `npm run bench` measures it.
  A `state.json` from before the split is split on first start and renamed to `state.json.migrated` only after every session reads back (`#split`), and `test/session-files.test.js` proves the split from real fixtures written by the old code, never hand-written ones.
- Delivery is at-least-once.
  `#answer` in `src/session-store.js` moves a batch from `pending` to `unacked` and holds it there until a later poll's `ack` cursor (its high `uid`) confirms receipt; a fresh poll redelivers an unacknowledged batch, an event-woken poll does not, so a lost response redelivers by `uid` and two pollers never split one batch.
  `pointback poll` threads that cursor through `poll-cursor.json` in the state dir (`readPollCursor`/`writePollCursor`), keyed by the canonical path and carrying the session `epoch`, writing it only after the batch is on stdout; eviction starts a new epoch, whose uids number on from that cursor's so none repeats for the file, and the server ignores an ack from another epoch.
  A moved or deleted file is found through `canonicalPath` and answers `gone` (HTTP 410) to poll, reply and end.
  A tab must hear every change to what it shows: a `gone` from poll or end resets the watcher's baseline (`missing` in `src/watch.js`), or a file renamed back inside the 100 ms debounce reads as no change and the tab stays on its notice; an open under another `--root` sends `rerooted`, or a live tab reloads into a 404.
  `test/events.test.js` pins both.
  A save made while no event stream follows the review is numbered when the next stream opens (`catchUp` in `src/session-store.js`, called by `#watch` in `src/events.js` once its watch is on).
  The watch runs only while a stream is open, and a new one takes the file as it finds it for its baseline, so a save between a reload's stream closing and the next opening, or between a review's open and its first stream, never reached a page already showing the file before it.
  Windows widened that gap: `windows-flake-hunt` jobs 114919289123 (a reload) and 115213131684 (a first open) each had the chrome's first stream connect fail with `net::ERR_NO_BUFFER_SPACE`, then followed the review at revision 0 and never asked for `?r=1`.
  `test/events.test.js` and `test/browser.test.js` ("a save made while ...") force the close, save, open order.
  The note card is composed in the chrome, never in the artifact (`src/browser/chrome.js`); the artifact proposes a target, heard only while Annotate is on and no card is open, and the chrome copies its fields by name and reads the instruction from its own textarea, so a hostile page can neither forge nor rewrite a note.
  `test/browser.test.js` asserts that as a property, against pages proposing every field a note has; `test/server.test.js`/`test/session-store.test.js` prove redelivery.
- A poll is a run of requests (`poll` in `src/cli.js`), each held at most `limits.pollRequestMs` (240000) before the CLI asks again, until `--timeout-ms` passes or an answer comes; the server's own ceiling is `limits.pollTimeoutMaxMs` (600000).
  Node's fetch gives up on a response whose headers have not arrived in 300 s (undici's `headersTimeout`), so through 0.1.6, which held a poll as one request, every `--timeout-ms` above 300000 ended at 301 s in `error: fetch failed`, exit 1.
  Measured on Node 26.10.0 (undici 8.10.2) against one daemon: the 0.1.6 CLI at 400000 exited 1 at 301 s, a bare `fetch` of the same poll failed at 301 s with cause `UND_ERR_HEADERS_TIMEOUT`, and `node:http`, which has no such timeout, held it to `waiting` at 400 s.
  Raising the client's limit instead needs undici as a dependency or a second HTTP client on `node:http`, and still loses a single long request to anything between that cuts one sooner; bounded requests need neither, and a note arriving between two requests is answered at once by the next (`waitForFeedback` in `src/session-store.js`).
  `test/cli.test.js` proves it scaled down, with requests held 300 ms: a poll request that asks the daemon to hold it past 1 s fails as Node's fetch would (`test/helpers/fetch-limit.js`), a 3000 ms poll answers `waiting`, exit 0, and a note sent once the first request has been answered is delivered.
  The limit is decided from what the request asks for, never timed: a timed 1 s limit left 700 ms of slack over a 300 ms hold, and on run 37248292741, attempt 5, a starved `windows-2025` runner spent it and failed the poll with "The operation was aborted due to timeout".
  A request that ends with nothing keeps its poll counted for `limits.pollGraceMs` (2000), and the next request takes its place (`#attach`/`#detach` in `src/session-store.js`): without that, the pill and its `role="status"` line went from "Agent listening" to "Agent away" and back at every request boundary, once per 240 s, and a session in the gap between two requests could be evicted.
  `test/session-store.test.js` pins the events under mocked timers, and `test/browser.test.js` reads every state the pill takes through fifteen 200 ms requests: `waiting`, then `listening` for the whole poll, then `waiting` once the grace passes.
- The daemon never closes an idle keep-alive connection on Node's timer (`keepAliveTimeout = 0` in `serve`, `src/server.js`), so the browser always closes first; the 30 min idle-out is the only close.
  Node closes an idle connection after 5 s by default plus a buffer: Node 26.10.0 and Node 24.11.1 both report `keepAliveTimeoutBuffer` 1000 and advertise `Keep-Alive: timeout=5`, and a server with Node's default `keepAliveTimeout` and the daemon's `headersTimeout` closed an idle keep-alive connection after 6001 ms on both.
  WebKit sends a request on an idle connection even as the server closes it, does not honour the `Keep-Alive: timeout` the server advertises, and never retries a POST or DELETE that dies there; the chrome then shows `Could not add the note: the review server did not answer` while its stream is live, so the bar still reads `waiting` ("Agent away") or `listening`.
  Measured with WebKit 26.6 against the daemon with its idle close lowered to 100 ms: 103 of 2500 POSTs failed with `TypeError: Load failed`, each sent 1.5 to 3 ms before the close; Firefox 155 lost 0 of 300.
  With nothing closing from the server, WebKit reused a connection idle 28 s and opened a new one at 30 s, and Firefox reused one idle 60 s.
  Against the daemon itself (`keepAliveTimeout` 0, `headersTimeout` 30 s, `requestTimeout` 610 s), a connection idle 620 s got a 200 on the same connection on Node 26.10.0 and on Node 24.11.1.
  Scaled down (`keepAliveTimeout` 0, `headersTimeout` 1 s, `requestTimeout` 2 s), a connection idle 8 s was reused on both versions.
  A connection that never sends a byte, opened against the daemon itself (`headersTimeout` 30 s, `keepAliveTimeout` 0), was still open after 45 s on Node 26.10.0 and on Node 24.11.1.
  On main at 8a78d73, with Node's default `keepAliveTimeout` 5000, `keepAliveTimeoutBuffer` 1000 and `headersTimeout` 30 s, a connection that never sent a byte was still open after 45 s on Node 24.20.0, on Node 24.11.1 and on Node 26.10.0; all three behaved the same.
  What can hold one open is bounded for a loopback review server: a browser keeps a bounded pool of connections to each of the daemon's two loopback names and drops each at its own idle window, a crashed client's sockets are closed by its operating system, and the daemon's idle-out closes every connection (`close` in `serve`).
  Known boundaries, with no code change: `server.maxConnections` is unset, so idle sockets are bounded by the process file-descriptor limit and the daemon's 30 min idle-out.
  The idle-out itself closes connections and could race an in-flight POST; a visible tab heartbeats every 10 min (`idleMs / 3`), which keeps a reviewer on the page from reaching it.
  Sending `connection: close` on every response was tried first and reverted: a connection per request ran Windows out of sockets, and run 37278582222 (runner `windows-2025`) failed 3 of 20 browser-suite attempts with `net::ERR_NO_BUFFER_SPACE` on a drafts POST or a script load.
  A longer finite timeout bets on every engine's undocumented idle window, and a client retry needs an idempotency key on every write route.
  `test/server.test.js` holds a connection idle 6.5 s and sends an add on it, and `addAfterAnIdle` in `test/engine-smoke.js` does the same through the note card in WebKit and Firefox and checks the add arrived on a connection opened before the idle.
  Both fail on the code before the change, which closed the connection at 5 to 6 s.
  The 6.5 s idle sits above the 6001 ms close on both Node versions, and the new server test also passed on Node 24.11.1.
  A test that mocks `setTimeout` sends its HTTP through `node:http`, never `fetch`: on Node 24.20.0 (undici 7.29.0) a `fetch` reusing a kept-alive connection under a mocked `setTimeout` stalls until the server closes that connection, which on 24.11.1 (undici 7.16.0) and 26.10.0 (undici 8.10.2) it does not.
  Before this change Node's 6 s keep-alive close freed the stalled request, so the idle-out test's steps took 6125 ms on 24.20.0 instead of failing; after it the test hung to its 60 s timeout on macOS hunt run 37285432454 (runner `macos-15`, node v24.20.0 read from its job logs, 20 of 20 attempts timed out) and on cross-platform run 37285441453, job `macos-15 / node 24` (runner `macos-15`, node v24.20.0, one job, which timed out the same idle-out test at 60 s), while ubuntu hunt run 37285428264 (runner `ubuntu-24.04`) and windows hunt run 37285436954 (runner `windows-2025`), both node v24.21.0, passed all 20 attempts each, in 114 to 242 ms on ubuntu and 282 to 676 ms on windows.
  With real timers the idle-out closes a silent client's kept-alive connection: with a 300 ms window the daemon released at 346 to 359 ms on 24.20.0, 24.11.1 and 26.10.0, and the test now asserts that close.
- The agent answers a note with `pointback reply <file> <uid>`: the reply is stored on its chat entry (`reply` in `src/session-store.js`), reaches tabs as a `reply` event, and is set as text, never HTML, in the margin (`replyLine` in `src/browser/chrome.js`).
  A tab learns of sent notes only from the stream: the `drafts` event that empties the drafts carries them as `sent` (`#draftsChanged`), and Send and End never refetch the session, because a refetch raced the stream, emptied the margin until it landed, and one answered before a reply wiped the reply off its note; `test/browser.test.js` holds every response to prove it.
  A change to the drafts adopts its own answer only if the stream set no drafts while it was in flight (`changeDrafts`): always adopting it put a sent note back, never adopting it left the send key with nothing to send while the stream lagged, and the browser suite holds the answer and the stream in turn to pin both.
  A send in flight holds its notes' ids (`sending`), and a `hello` or `current` ends it only once the drafts no longer list them: one landing before the server had the send re-offered the notes it was sending.
  `skills/pointback/SKILL.md` is the agent-facing copy of the CLI contract and ships outside the npm package, so change it with any command, flag or field it names.
- A reviewer's work survives the tab and the daemon.
  Unsent notes are drafts on the session (`addDraft`/`send` in `src/session-store.js`), never tab storage, and a restart reuses the port and token in `server.json` so an open tab reconnects (`serve` in `src/server.js`, `listen` in `src/browser/chrome.js`).
  A restart whose recorded port cannot be had takes a new one, and Windows refuses such a bind with `EACCES` where another account's socket, or an exclusive one, holds the port on the wildcard address (`PORT_GONE`).
  On EADDRINUSE alone, windows-2025 hunt 38316222104 job 115033372086 had every open on the cli suite's shared directory exit 1 with nothing printed, two minutes after a test stopped its daemon: each restart died on `listen EACCES` for the recorded port.
  Because the token outlives the process, nothing may present it to a server that has not answered a fresh challenge with `tokenProof` (`src/http-guard.js`): the CLI's `health` and the chrome's `health` both check it first, the chrome's `connection`, which `api` requires, goes live only on a proven answer (`boot` and `listen` in `src/browser/chrome.js`), and a token shown to an unproven server, or carried to a new port, is replaced.
  `test/cli.test.js` asserts a squatter on the old port sees nothing but the challenge, and `test/browser.test.js` that a tab whose health check is answered without proof sends nothing carrying the token.
- The artifact frame is opaque-origin, so every asset load from it is a CORS request.
  Only a font under the root (`FONT_HEADERS` in `src/http-guard.js`) and the daemon's own vendored house faces, which a rendered Markdown page loads, are served with `Access-Control-Allow-Origin`, never the page, another file or the API: the frame has unrestricted egress, so widening it lets a hostile page read and send out anything under `--root`.
  `test/browser.test.js` and `test/server.test.js` fail on either side of that line.
- A review shows HTML or Markdown and refuses anything else at open with a 415 (`artifactKind` in `src/markdown.js`).
  Markdown is rendered by markdown-it with raw HTML on, in `src/browser/markdown.css`, and every block carries `data-source-lines`, which the SDK turns into a note's `lines` (`sourceLines` in `src/browser/sdk.js`); the store keeps `lines` only on a Markdown session's notes, so an HTML page carrying the attribute names nothing.
  `test/browser.test.js` proves both against a copy of `README.md`, which is therefore also a fixture: its Install paragraph opens with `` `parse5` ``.
- A review's page is rendered, parsed and injected once for each content its file has (`page` in `src/session-store.js`), keyed by the SHA-256 of the file's bytes, and the open, every connect and every fetch read that one copy.
  Through 0.1.7 each of them did the work again: for a 1.3 MB Markdown file (4.3 MB rendered), every artifact GET took 0.39 to 0.45 s and a `/health` sent behind one waited 0.43 s; served from the copy, the same GETs took 0.010 to 0.030 s and `/health` 0.009 s.
  The key is the content and never the file's mtime or size, so an edit is never served stale, and the copy holds what the page loads as it names it rather than a verdict, because whether that is outside the root depends on the root, which a later open can change.
  A stylesheet the page links from under the root is read again on each ask (`readSheet` in `outside`), so an edit to the sheet alone is never missed, and what it loads by CSS `url()` or `@import` is resolved from the sheet's own address (`assetsOutside` in `src/inject.js`); through 0.1.7 only markup attributes were read, so a font named in `@font-face` from outside the root painted as a silent fallback (`test/cli.test.js`).
  `test/server.test.js` counts renders through markdown-it's `parse`: one open, ten connects and ten fetches of one content render it once.
- The event stream is a WebSocket (`eventStream` in `src/server.js`, `src/websocket.js`, `follow` in `src/browser/chrome.js`).
  As a held `fetch` response it took one of the six HTTP connections a browser allows a host, so with five other review tabs open the sixth tab's add hung for good and the seventh never loaded (`test/browser.test.js`, "eight review tabs"); WebSockets have their own pool.
  Releasing the stream while a tab is hidden was rejected: it breaks `live` for duplicate tabs and still fails with six visible windows, and HTTP/2 needs TLS.
  The token rides as the offered subprotocol `bearer.<token>`, a refusal the tab acts on is a close code after the handshake (4401, 4404, 4429), and every API call carries a 10 s deadline so no add, edit or send waits on a queued request without saying so.
  A tab counts its stream open at the `hello`, never at the handshake: a 4429 comes after the handshake, and counting that open reset the backoff, so a tab past `limits.eventStreams` tried 106 to 118 times a minute in all three engines and said the server had stopped answering.
  It now backs off to the 5 s cap, says too many review tabs are open, and tries only while visible, because every try touches the daemon and a hidden tab held it awake for good (`test/browser.test.js`, "a tab refused for too many event streams").
- A key the chrome acts on is `preventDefault`ed.
  On macOS Chromium offers an unhandled key to its menus as a key equivalent, and a headless browser blocks there in `SLSObscureCursor` and freezes whole; the note card's Escape did that on its second press (`test/browser.test.js`, "Escape closes the note card"), and a headed browser never shows it.
  A headless browser on macOS also sends a key the page leaves unhandled back to the page, again and again, when the key carries the native key code `key` in `test/helpers/cdp.js` gives it: one `o` and one `k` typed with the page's focus on a paragraph reached the page as 26 and 15 keydowns in 2 s in Chrome for Testing 153, and once each headed or without the native code (transcripts "probe: Chrome for Testing 153 ...").
  So a test types into the page only once the element meant to take the keys holds the focus, as the page and the chrome see it; "keys the page takes with no note open" makes the focus land late, and typing at once read `keydown o` three times there, as on macos-15 in hunt 37308882779, attempt 2.
- Only the page under review announces itself (`ready` from the SDK), so a frame `load` without one is the frame gone somewhere else, a followed link or a missing page; the chrome covers the frame with a notice and Back (`strayed` and `renderCover` in `src/browser/chrome.js`), and a missing path inside a review answers with `src/browser/missing.html`, never JSON.
  The first load after each show that comes back unannounced is shown once more before it counts as a stray (`firstLoad` and `shownAgain` in `pageLoaded`), unless `holdsReload` holds the reload back for a note, and the wrapper's first load gets the same one more chance when it ends without the wrapper announcing itself; a session fetch at boot that nothing answered waits like an unanswered health check, and only an answer calls the link dead (`boot`).
  Each is a refused loopback connect a Windows reviewer meets (below): before this, a refused page or SDK load showed the stray cover, a refused wrapper left Chrome's error page in the frame with the help line still saying to click the page, and a refused session fetch said "This link no longer works" about a link that worked.
  "a refused first load of ..." in `test/browser.test.js` refuses one load of each over CDP Fetch, and all four failed before the change; "a page under review that never loads" pins the bound: two loads, then the cover.
  A frame's load is judged one message later than its load event, through the judging window's own `postMessage` (`loaded` in `src/browser/wrapper.js`, `wrapper-loaded` in `src/browser/chrome.js`), because HTML queues the load event on the DOM manipulation task source and a posted message on the posted message task source, and leaves their order to the browser.
  A message queued from the load event lands behind the frame's announcement already in the queue.
  Judged at the load event itself, WebKit 26.6 heard the page's load before its `ready` and the wrapper's load before its announcement, so it showed every page twice in a wrapper loaded twice (20 of 20 opens), and Firefox 155 loaded the wrapper twice (20 of 20); Chromium 155 loaded each once.
  The second page replaced the frame under whatever the reviewer was doing in the first, which failed the WebKit engine smoke on CI with "Execution context was destroyed" (main f58fd8a, job 114738696906).
  `coreAct` in `test/engine-smoke.js` and "a review whose loads all answer asks for the page under review and the frame it is shown in once each" in `test/browser.test.js` count the loads.
- A refused file of the chrome's own (`chrome.js`, `radiogroup.js`, its five sheets, its two faces) reloads the chrome once (`src/browser/recover.js`, its first script, before any file it watches is asked for), and the load that reload starts spends a single-use list in the tab's `sessionStorage` of the files the reloads so far were for, so it reloads again only for a file not on it: a file that never loads costs one reload, a chain of reloads ends within the chrome's own files, and a reviewer's own reload starts a new list; a refused link of the page under review is asked for once more where it failed (`ASK_AGAIN` in `src/inject.js`, first in the page's head); the wrapper has no sheet, since `wrapper.js` sets its few styles, and its refused script is the wrapper load already asked for again above; the chrome's own page is asked for again by the browser, which reloads a page that failed to load.
  `recover.js` is a file rather than inline because the chrome's CSP allows only its own scripts; refused itself it costs nothing, since it only acts when another file fails in the same load.
  A file refused while `navigator.onLine` is false, or while the chrome's connection is not live, waits to reload until the browser is back online and the chrome reconnects: the browser refuses that reload too and puts its own error page where the review was, which is how a face still loading when a test took the tab offline lost the review on runs 38219818479 (`macos-15`, job 114713089540) and 38227307855 (`ubuntu-24.04`, job 114737869044), and a review evicted meanwhile is never reloaded, so the tab says it is gone.
  The chrome says the browser is offline while `navigator.onLine` is false, since an open event stream can outlive it ("a chrome face refused while the browser is offline" in `test/browser.test.js`, `faceRefusedOffline` in `test/engine-smoke.js`).
  A refused face is heard by the rejection of its `loaded`, never by `loadingerror`, which WebKit 26.6 never fires: it fires no `FontFaceSet` loading event at all.
  Measured under Playwright 1.63.0 with the chrome's code face refused once, 10 runs per abort code: on 0.1.7 none of 30 reloaded (26 left the face `error`, 4 `unloaded`); watching `loaded` reloaded 28 of 30 with the face painted.
  The other 2 were `timedout` aborts that WebKit put back to `unloaded` with `loaded` still pending, which nothing reports, so a refusal WebKit treats that way still leaves the fallback face until the reviewer reloads.
  Plex Mono is first set in the file name, which is filled in once the review is fetched, so a refused code face reloads the chrome just after it is ready, before anything can be typed.
  A reload that a refusal asks for while a note is being written, or a margin note is being edited, waits for the hold the chrome registers with `recover.hold` (`holdsReload`, or an open margin edit), and lands when the note or edit closes, so the typed text stays; `"a chrome face refused while a margin note holds typed text ..."` pins the composer card and `"a chrome face refused while a margin note edit holds typed text ..."` the margin edit, both in `test/browser.test.js`.
  Before this each left the reviewer on a dead page (`chrome.js`), an unstyled one (a sheet), the system fallback face, a text size whose arrow keys did nothing (`radiogroup.js`), or an unstyled page under review; "a refused first load of ..." refuses one load of each and compares the review with one whose loads all answered (computed styles of the chrome and the page, the faces drawn, the text size's arrow keys), and the eleven new rows for a chrome file or a page's sheet failed on main, while the chrome page's own row passed there, recovered by the browser; "a file of the chrome's own that never loads" pins the bound: two loads, one reload.
  A row expects one reload for each of the chrome's loads that met a refused file of its own, counted from the loads that failed, because forcing the first refusal leaves the reloaded load open to a refusal of the network's own on any of its other files: windows-2025 hunt 38168177233, attempt 20, met one on the house's components, which left Send in the browser's own style while a single reload was the bound; "a different file of the chrome's own refused on the load its recovery made" pins the second reload, and failed on that bound.
  A row counts the reloads the chrome asks for itself (`Page.frameRequestedNavigation`, reason `reload`), never the navigation entry of the document it ends on: Chrome on macos-15 labels the browser's own reload of the error page a refused chrome page leaves `reload` there, in 20 of 20 jobs of run 37388410319 with the chrome asking for no reload, where Chrome on Linux and Windows and Brave label it `navigate`.
- Browser-side code (`src/browser/`) is served as static files, is excluded from coverage, and is tested only by the real-browser suite in `test/browser.test.js`.
- The browser suite is the one part that a restrictive sandbox still breaks, so run `npm run check` from an ordinary shell: it launches a headless browser that binds a process-singleton unix socket, which a sandbox denying `AF_UNIX` bind refuses.
  `fs.watch` fails under such a sandbox too, with `EMFILE: too many open files, watch` on the first event, but `watch`, `events` and `server` survive it: `test/helpers/watch.js` decides watch support by watching a real file with the product's own watcher, and each test that depends on it states which path it is exercising and asserts that one.
  The probe calls watching unavailable on an error at once, but on silence only after 40 writes and 10 s, as `until` bounds a wait.
  Its first form wrote once, 20 ms after the watch began, and gave up at 10 s on the clock; under full-suite load on macOS it spent the whole deadline and sent three `events` tests down the `reload-off` branch on a machine that watches.
  Both halves were wrong: a watcher arms on its own thread after `fs.watch` returns, so a starved process loses a write made before it is armed (12 probes at background QoS beside a 128-thread burn: 9 and 5 answered unavailable at 10 s, while every one that answered available did so inside 1.7 s), and a process held off its loop past a clock-only deadline runs the deadline before the change waiting behind it ("the suite's watch probe gives a process held off its loop ..." in `test/watch.test.js`).
  Eight copies of `test/events.test.js` at background QoS beside a 128-thread burn failed 8 of 8 that way on the first form and passed 8 of 8 on this one.
  The product holds no such deadline: `src/events.js` says `reload-off` only on the watcher's error, and a reviewer saving five times beside a 128-thread burn saw every save painted and no notice.
  Never assert on the next line of an event stream in those suites.
  `src/events.js` turns a failed watch into a `reload-off` on the same stream that carries `superseded`, so a test taking whichever line arrives next reports the identical result whether the behaviour it exists for works or is broken - which is how one sandboxed `superseded` assertion spent a day being read as a known environment artifact.
- WebKit and Firefox are covered only by `npm run smoke` (`test/engine-smoke.js`, Playwright through `playwright-core`), weekly and on the release pull request by the `engines` job in `.github/workflows/cross-platform.yml`, where a red engine fails `checks` and holds the release (maintainer decision), and skipped on `release.yml`'s push to `main`, so the tag waits on the platform matrix alone; never import Playwright into `test/*.test.js`, which stays on the CDP harness.

## CI runner platforms

A pull request runs Linux runners only.
GitHub bills a macOS minute at about 10x a Linux one and a Windows minute at about 1.67x, all against the same allowance, so a three-platform matrix on `pull_request` spends most of the budget proving what the cheapest runner already proved.
macOS and Windows coverage lives in `.github/workflows/cross-platform.yml`, on a weekly `schedule:`, on `workflow_dispatch`, and through `workflow_call` from both `ci.yml` and `release.yml`.
Do not add a `macos-*` or `windows-*` runner to a job that runs on `pull_request`, with the one exception the `cross-platform` job in `ci.yml` already is: that pull request alone calls the matrix, guarded on `startsWith(github.head_ref, 'release-please--')` and same-repository head, and every other one skips it.
Every push to `main` runs the matrix too, and that is not optional: it is what gates the tag.
Nothing in this repository may create a tag or a GitHub release until all three platforms have passed in the same run, and `release-please` is therefore split across two jobs by its own skip inputs - `release-pr` (`skip-github-release: true`) in front of the matrix so the release pull request is still opened, `release-tag` (`skip-github-pull-request: true`) behind it as the only job that can tag.
Never condition that matrix on whether the push looks like a release: release-please owns that answer, and a second opinion answering "no" wrongly skips the matrix, skips `release-tag` with it, and drops the release in silence.
Two empty releases came from getting this wrong - v0.1.0 on run 33822348514 and v0.1.1 on run 33859541647, both `assets: []` - and `test/pipeline.test.js` now pins the ordering; `docs/GIT-WORKFLOW.md`, "Releasing", carries the measurement.
The step that runs the suite carries its own `timeout-minutes`, always smaller than its job's, and `test/pipeline.test.js` pins that: a step over budget fails and reports a verdict, while a job over `timeout-minutes` is reported `cancelled`, which the `checks` aggregate can only refuse.
Never add `cancel-in-progress` to a release, publish, or scheduled workflow: cancelling a publish mid-flight causes real damage, and a superseded scheduled run is the only record of its own result.
`.gitattributes` pins the working tree to LF everywhere, because the Windows runner checks out under `core.autocrlf=true` and `prettier --check` then refuses every text file in the tree; that, not a missing browser, is what failed `windows-2025` on the 0.1.0 release, and `test/pipeline.test.js` pins the file.
Chrome is present on all three runner images, and both workflows resolve it through `KNOWN_BROWSERS` in `test/helpers/cdp.js` rather than naming a path, so a moved binary is one edit there.
Never quote a glob in a `package.json` script: npm runs a script through `cmd.exe` on Windows and cmd keeps the quotes, so `'test/*.test.js'` reached `node --test` with its quote characters, matched nothing, and passed `windows-2025` green over zero tests on run 33824393013.
Each leg reports in its own job summary which browser it drove, and a leg that reports no verdict fails; that is the guard against the same silence going green again.
All three platforms pass the whole suite; keep it that way by reading the two Windows entries under "Working here" before touching a path, a spawn or a file mode.
